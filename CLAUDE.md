# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Research code (see `Paper.pdf`) that builds multi-day tourist itineraries for Rio de Janeiro using two of the authors' techniques: Greedy and GRASP. The paper's Random and Iterated Tabu Search (ITS) techniques were removed from the code. It is an experiment runner, not a library or app: one run executes every technique under every parameter combination and appends the results to a text file. The README and code comments are in Portuguese.

## Setup and running

- `requirements.txt` lists the dependencies without pinned versions:
  - Core (`src/`): `numpy`, `pandas`, `tqdm`
  - Analysis notebook: `matplotlib`, `scipy`, `jupyter`
  - `scripts/build_distance_matrix.py` also needs `scipy`, plus `osmium` (for `--pbf`) or `osmnx` (for Overpass). The last two are not in `requirements.txt`.
- The README targets Python 3.11 in a conda env named `route_generation`.
- Run from the **repo root**: `python src/main.py`. Every data path is relative to the current directory (`Input/`, `Parameters/`, `Results Analysis/`).
- Package imports such as `from heuristics import ...` resolve only because `src/` is the script's directory. To import modules any other way, use `PYTHONPATH=src`.
- **The distance matrix is not the authors' original.** `main.py` reads `Input/RJ_distance_matrix.txt` (tab-separated, with a `Place Names` index column and POI URLs as keys). The authors never published theirs. The current file is a stand-in generated by `scripts/build_distance_matrix.py`, which works from the CSV coordinates using OSM walking distances. With `--pbf <file>` it reads an OSM extract offline: the Geofabrik `sudeste-latest.osm.pbf` takes ~2 min and ~2.6 GB of RAM. The BBBike Rio extract leaves out the Zona Oeste. Without `--pbf` it downloads from the Overpass API, and `--method haversine` uses straight-line distances. It also fixes coordinates stored ×1000. It drops the 27 places outside the municipality, using the IBGE boundary in `Input/RJ_boundary.geojson` with a 100 m margin for the simplified coastline, which leaves 2,138 places. It also lists the places that are far from any street (islands such as Paquetá, and bad coordinates). `.gitignore` excludes `Input/*.osm.pbf` and `cache/`.
- `main.py` converts names to IDs with `.map(codes).astype(int)`. The original `.replace(codes)` relied on pandas silently downcasting the result to `int64`. pandas 2.2 deprecated that and 3.0 removed it, so the IDs stayed `object` dtype and the numpy indexing in `select_hotel` failed.
- **Tests:** `pytest` (config in `pytest.ini`, tests in `tests/`, run from the repo root with `.venv/bin/python -m pytest`). They use only made-up data and no network. `-m "not slow"` skips the ones that build or run the C++. They cover the Yelp converter, the comparison report, an end-to-end run on a fake city, and two Rio regression checks: the re-exported `RJ_instance` is byte-identical, and GRASP v4 `--seed 1` reproduces the first rows of `My Results/RJ/rio/results_v4.txt`. There is no linter config. `check_results` is still the check for any new GRASP version. Most Python files are Black-formatted; `src/model/checkins.py` uses tabs.
- For a quick run, lower `amount_executions` in `Parameters/experiments.json` (default 100). Every run executes both techniques. To run only some of them, edit the `techniques` dict in `opt_call.py`.
- **Results layout (one folder per city, reorganized Nov 2026 at the user's request):**

  - `Results Analysis/Authors/RJ/original/` holds the authors' own files (their notebook, `resultados_finais.txt`, their old `results.txt` and the PNGs in `Results/`). They were produced with the authors' unpublished distance matrix, so their route IDs do not match the current one. Do not write new runs there.
  - Result files are only appended to, never truncated, and `write_results` creates the folder if it is missing. Don't append to the Rio reference files.
  - `My Results/RJ/rio/results_v2.txt` holds two full runs appended one after the other (from before the reorganization), which is why the report counts 3600 v2 rows.

## C++ GRASP (`cpp/`)

The authors' GRASP in C++. The user is improving it **one versioned fix at a time**, to measure each change in isolation. `cpp/README.md` (in Portuguese) has the version table and the bug list. In the code, fixed bugs are marked `// CORRIGIDO:` and the ones still kept are marked `// ORIGINAL:`.
- **Fixes go only in `cpp/`.** The Python GRASP in `src/` is the authors' baseline and still has every bug in `cpp/README.md` (≈25–28% of its routes break the distance limit). Python changes so far only extracted `prepare_data` and `build_places_parameters` for the exporter and added `main.py --city/--output` (passed down to `generate_experiments`), without changing logic.
- **Versions.** The user chose to fix the translation in place, not to keep it alongside.
  - The **literal translation** lives in commit `70eb95a` and was **bit-exact with Python**. With `--seed 1` it reproduced all 1800 GRASP rows of `Authors/RJ/rio/results_python.txt`, columns other than time. `numpy_compat` provides this: numpy's legacy MT19937 RNG, masked `randint`, `random_sample`, `choice` with or without `p`, pairwise `np.sum` and `str(np.array)`.
  - **`GRASP_v1`** (commit `c09da9d`) fixes the local-search feasibility: the real position, an exact day distance via `day_route_distance` including the hotel return, and budget/distance updates. Its routes therefore differ from Python's.
  - **`GRASP_v2`** (commit `32fdc39`). Its local search ranks the candidates with `order_candidates` and tries them in order until one fits.
    - **Δ** = d(A→N) + d(N→C) − d(A→P) − d(P→C), where C is the hotel for the last place of the day.
    - **Group Δ ≤ 0** comes first, highest rating gain first. The plain Δ/gain ratio would favor small gains when Δ is negative.
    - **Group Δ > 0** follows, lowest Δ/gain first.
    - It draws no random numbers; remaining ties go to the lowest ID.
    - The user considered keeping distance slack, the ratio, for later swaps. Simulations showed the slack buys few extra swaps in a single pass. Revisit this if an insertion move or multi-pass local search is added.
  - **`GRASP_v3`** (commit `aede8fa`). It seeds each execution with the authors' Greedy route as the initial best.
    - A GRASP iteration replaces the seed if its fitness is ≥ the seed's (user's choice). Among GRASP solutions the usual `>` rule applies.
    - If no 5-star hotel fits the budget, the Greedy throws `GreedyHotelNotFound` (Python raises IndexError) and the GRASP runs unseeded.
    - The Greedy draws no random numbers, so each v3 result equals `max(v2, Greedy)` row by row. This was verified on all 1800 rows.
    - Output has a **7th column** with the origin (`greedy`/`grasp`). `check_results` shows it as `do_grasp`, and it is the way to report GRASP's own merit, since v3 ≥ Greedy holds by construction.
  - The **current version is `GRASP_v4`**: v3 plus a reactive α that actually reacts. `alpha_probabilities` uses Prais & Ribeiro's maximization rule `q_i = (A_i/z*)^δ` with δ = `REACTIVE_AMPLIFICATION` = 10, replacing the authors' minimization formula + "inverse probability" (≈20% each for 5 alphas). It still draws one random number per selection.
    - **Result: no significant change vs v3** (|t| < 1.4 in all 18 groups, same speed, 100% feasible). The user chose to keep it anyway as the correct formula, with the negative result documented.
    - Reason: on this instance α barely matters. Fixed α 0.1–0.9 and δ = 1/10/30/100 all land within noise (σ ≈ 0.5). Don't expect gains from α-selection tweaks.
    - Untried improvement measured during review: ordering local-search candidates by rating gain first (ties by smallest Δ) instead of the v2 Δ≤0-first groups gave +0.10 to +0.44 in all 12 groups below 45, still 100% feasible. It is a candidate for the next version.
  - Each version must write a distinct algorithm label (`GRASP_NAME` in `heuristics/grasp.hpp`) and a distinct default output file, so earlier results are never overwritten. The user asked for this explicitly.
  - Keep `-ffp-contract=off` and preserve the order of floating-point operations and random draws in code that isn't being changed. This keeps each version's effect attributable to its change.
- **Greedy in C++** (`heuristics/simple_greedy.cpp`, `cpp/build/greedy`) is a **literal translation**. The user asked that its logic never change. It reproduces the 600 Greedy rows of `Authors/RJ/rio/results_python.txt` exactly. Its tie order comes from `greedy_order.txt`, written by the exporter with numpy's own `np.flip(np.argsort(...))`, because numpy's argsort leaves tie order unspecified.
- **Comparability rule (user decision).** New versions may change *how* the problem is solved, but never the problem rules, because the user compares against the authors' results.
  - **Keep the authors' cap of `amount_daily_places − 1` places per day.** That is 4, so fitness is at most 45; the paper defines 55. Do not "fix" it.
  - **Keep the construction's per-day-total category count.** With 4 places/day it is equivalent to the paper's consecutive rule.
  - **Only as a separate, explicitly requested track:** 5 places/day or other rule changes. Compare such a track only within itself, or normalize by its own maximum.
- **Data.** `scripts/export_instance.py` runs `main.prepare_data` and `opt_call.build_places_parameters`, which were extracted from the old inline code without changing their logic. It writes `Input/RJ_instance/`: `places.tsv`, `hotels.txt`, `places_available.txt`, `greedy_order.txt`, `names.tsv` (id, name, original CSV type for attractions; display only) and `distance_matrix.bin` (float64, row-major). The folder is gitignored. Re-export whenever `RJ.csv` or the matrix changes.
- **Build and run** from the repo root:
  - `make -C cpp` builds one executable per file in `cpp/src/apps/` into `cpp/build/` (gitignored). The rest of `cpp/src/` is shared code. New programs, such as the user's own GRASP, go in `apps/`.
  - `cpp/build/grasp [--output F] [--instance D] [--seed N]` reads `Parameters/*.json` and appends to `Results Analysis/My Results/RJ/results_v4.txt` (outside `rio/`, so the reference is never appended to). Before each algorithm-parameter group it writes a `# GRASP_<version> max_iterations=N` line (Python doesn't). Each older version's file in `My Results/RJ/rio/` (`results_literal.txt`, `results_v1.txt`, …) holds that version's output; never append to it.
  - It is about 15× faster than Python.
- **Verifying a new version:**
  - Run `check_results` on its output. It must stay 100% feasible.
  - Compare the per-group mean fitness against the previous version and against the authors' feasible-only results.
  - Bit-exactness with Python can only be checked against the literal translation, by checking out `70eb95a`.
- **Feasibility checker:** `cpp/build/check_results <results file>` (`model/feasibility.cpp`).
  - It recomputes everything from the final route. It prints a per-group summary and saves it to `<file>_summary.txt` (override with `--summary`). It writes `<file>_checked.tsv` with one row per solution, including `origem` and a `roteiro` column with place names. It writes `<file>_roteiros.txt` with the best feasible itinerary per group, readable, with names (`operations/itinerary.cpp`). `#` comment lines become the `secao` column, and numpy-wrapped multi-line routes are handled.
  - Rule definitions chosen with the user:
    - Category: at most `category` **consecutive** places of the same category per day, as in the paper. The authors' code counts the daily total instead.
    - No repeated place in the **whole trip**.
    - At most `amount_daily_places` places per day, hotel excluded.
    - Distance includes the walk back to the hotel.
    - Tolerance 1e-6.
  - **Data caveat:** 45 places in `RJ.csv` are named "...: FECHADO" or "... - FECHADO" (closed on TripAdvisor), mostly restaurants. All algorithms, the authors' included, may pick them: 1393 of 3000 v3 solutions do. Filtering them would change the problem, so it needs the user's explicit decision under the comparability rule.
  - About 25% of the authors' final GRASP solutions are infeasible. Almost all violate distance; the cause is local-search bugs. All Greedy solutions are feasible.
  - `GRASP_v1` is 100% feasible. With default params and seed 1, its mean fitness beats the authors' feasible-only mean in all 18 groups (about +0.6). It still loses to Greedy when budget ≥ 1000 and distance is 20 km.
  - `GRASP_v2` is 100% feasible, including a 10,800-solution stress test.
    - It beats v1 in all 18 groups, +1.2 on average, reaching 44.6–45.0 at 100 iterations.
    - It ties or beats Greedy in 12 of 18 groups. It is just below where Greedy hits 45 (budget ≥ 1000, 20 km).
    - It is about 1.4× slower per execution than v1.
  - `GRASP_v3` gives 45.00 in every group where Greedy hits 45; elsewhere it equals v2. `do_grasp` is 100% in most groups. Where Greedy hits 45 it is 14–22% at 10 iterations, 61–77% at 50 and 81–95% at 100.

## Architecture

### Data flow

1. **`src/main.py`** prepares the data:
   - Normalizes the CSV columns: names become Title Case, `Category` becomes `General Category`, `Rating` becomes `Mean Sentiment`.
   - Collapses categories into `hotel`, `restaurant` and `attraction`.
   - Rewrites hotel URLs from `/Hotel` to `/0AHotel_` so hotels sort first.
   - Keeps only places that also appear in the distance matrix.
   - **Replaces every place name with an integer ID**: its position in the sorted name list.

   From this point on, a place is just an int. That int indexes the numpy `distance_matrix` and every per-place array, and hotels have the lowest IDs.
2. **`src/opt_call.generate_experiments`** builds the `places_parameters` dict:

   | Key | Contents |
   |---|---|
   | `hotels` | IDs of the hotels |
   | `price` | `Max Price` |
   | `rating` | `Mean Sentiment` |
   | `category` | general category of each place |
   | `distance_matrix` | the numpy distance matrix |
   | `places_available` | non-hotel IDs |
   | `df` | the full dataframe |

   The arrays are indexed by place ID. It then reads the three JSON files in `Parameters/`. Every value in them is a list, and `aux.explode_parameters` takes their Cartesian product to get one dict per combination. The loops run algorithm × algorithm-parameter combination × user-parameter combination × `amount_executions`.
3. **Output format.** Each execution appends one tab-separated line: `algorithm, budget, total_distance, time, fitness, route`. (Rows written before ITS was removed have two extra `None` columns, `remove_prob` and `tabu_size`.)
4. **Heuristic contract.** Each heuristic has the signature `func(places_parameters, users_parameters[, algo_parameters]) -> (route, fitness)`. To add a technique:
   - Register it in the `techniques` dict in `opt_call.py`.
   - Add it to the `algorithm == "GRASP"` check if it takes parameters.
   - Add it to `algorithm.json`.

### Route representations (two are in use)

- **`route_parameters` dict.** Produced by `heuristics/random_greedy_procedure.random_greedy` and also used by Greedy and GRASP. Its shape is `{"budget": total_cost, day: {"daily_distance", "restaurant", "attraction", "amount_places", "route": np.array([hotel, ...])}}`.
- **Flat route array.** The hotel, then each day's places, with the hotel ID repeated at each day boundary. It is built by `operations/constructive_operations.generate_route_array`.

### Model

- **Objective (maximized).** The sum of `rating` over the unique places in the route, hotel included (`model/objective_function.measure_fitness`).
- **User constraints** (`Parameters/user.json`):
  - `budget`: hotel price × `amount_days` plus each place's `Max Price`.
  - `total_distance`: a per-day limit that includes the walk back to the hotel. Units are meters; walking time assumes 1 m/s.
  - `category`: the maximum number of places of one category per day.
  - `amount_daily_places`
  - `amount_days`
- **Feasibility check.** Greedy and GRASP both use `co.verify_constructive_heuristic_constraints`.
- **GRASP.** Builds a restricted candidate list (RCL) whose cost is the distance from the last place divided by the place's rating, with threshold `cmin + alpha·(cmax − cmin)`. It is reactive: alpha ∈ {0.3, …, 0.7}, chosen by `select_alpha` after each alpha has been tried once. Each construction is followed by a swap-based `local_search`.
- **Dead code: `model/constraints.py` and `model/checkins.py`.** These model time windows and opening hours, but no heuristic calls them. They depend on keys that are never set (`places_parameters["hotel"]`, `["expend_time"]`, `users_parameters["datetime_start"]`) and on dataframe columns missing from `RJ.csv` (`Working Start/End/Day`). As a result, `start_time`, `end_time` and `travel_end` in `user.json` have no effect on the routes.

  - `Results Analysis/Authors/RJ/original/Results Analysis.ipynb` reads `resultados_finais.txt`: 9 columns (an extra `qtd_iteracoes`) and lowercase algorithm names.
  - The current code writes 6 columns with uppercase names to `results_python.txt`.
  - The notebook and the PNGs in `Results Analysis/Authors/RJ/original/Results/` still cover the authors' ITS and Random results.
  - The notebook maps (budget, total_distance) pairs to user profiles A–F.
